Reviewed: PR head `a4b54f8964` against base `8ad206d026`, on CPU with jaxlib 0.11.1
(Python 3.13). Method: full `tests/checkify_test.py` on PR, base, and the patched

This branch carries the review plus two validated commits on top of the PR head:

1. `[checkify] fix code-namespace holes and remove _PLACEHOLDER_CODE`
2. `[checkify] make placeholder-effect insertion order deterministic`

112/112 tests pass on the branch (the 110 from the PR plus two new regression
tests, which fail on the unpatched PR head).

---

## Verdict

**The design is right and the PR fixes a real problem.** Moving code assignment
from a process-global trace-time counter to a discharge-time `CheckifyContext` is
the correct initial-style move, and the determinism win is bigger than the title
suggests: base produces different lowered text on *every fresh trace* of the same
function even single-threaded, so identical programs miss compilation caches. On
the PR, lowered text is stable across fresh traces, 16 threads, processes with
different `PYTHONHASHSEED`, and x64 mode.

**But the re-injection remap is built on an invariant two code paths violate.**
`check_discharge_rule` assumes an inner error's metadata keys are contiguous
`[0..N)`; checks under a disabled error category (F1) and while-loop cond checks
(F2) both burn codes whose metadata never surfaces, leaving holes. Re-injecting
such an error makes a later check silently steal the metadata of a check that
actually fired — `err.get()` then reports the message of a check that *passed*.
Both are regressions against base, both have small validated fixes, and
`_PLACEHOLDER_CODE` can be deleted outright in the same motion (F3).

| # | Finding | Kind |
|---|---------|------|
| F1 | Checks under a disabled error category burn a code, corrupting the namespace of re-injected errors → wrong message reported | bug |
| F2 | While-loop cond checkification burns a code with its error outputs discarded → same wrong-message collision, default config | bug |
| F3 | `_PLACEHOLDER_CODE` is only a discriminator flag; a fresh check is a unit namespace and the remap branch already handles it | simplification |
| F4 | "First error" ranking changes — one minor regression-ish, one improvement worth claiming | behavior change |
| F5 | `start_code` in the sub-jaxpr cache key trades cache reuse for uniqueness | perf note |
| F6 | Cross-process lowering nondeterminism survives the PR via `_add_placeholder_effects` set iteration | gap (pre-existing) |
| F7 | Smaller notes: recharge-TODO caveat, silent metadata merge, dead subfuns branch, `next_code` removal, CHANGELOG, contract change | notes |

## F1 — Disabled-category checks corrupt the code namespace (bug)

`check_discharge_rule`'s fresh-check branch allocates (`ctx.next_code()`) *before*
the `enabled_errors` test. A `checkify.check` inside
`checkify.checkify(f, errors=float_checks)` burns code 0, and since the recharged
error is discarded (the long-standing recharge TODO), its metadata is dropped: the
emitted `Error` has metadata keys `[1]` — a hole at 0.

On re-injection via `check_error` under an outer checkify, the remap branch
advances the outer context by `len(new_error._metadata) == 1`, so the remapped NaN
keeps runtime code 1 while the outer context hands code 1 to the next outer check —
whose metadata overwrites the NaN's in `Error._update`'s dict merge (new-wins,
silent).

```python
import jax, jax.numpy as jnp
from jax.experimental import checkify

def inner(x):
  checkify.check(x < 100., "dropped")      # user_checks not enabled: code 0 burned
  return jnp.log(x)                         # NaN check: code 1, metadata {1: nan}

err_inner, _ = checkify.checkify(inner, errors=checkify.float_checks)(jnp.array(-1.))

def outer(err, x):
  checkify.check_error(err)                 # advances outer ctx by len({1:...}) == 1
  checkify.check(x < 1000., "OUTER check")  # gets code 1 -> clobbers metadata[1]
  return x

err, _ = checkify.checkify(
    outer, errors=checkify.float_checks | checkify.user_checks)(
    err_inner, jnp.array(1.0))
print(err.get())
```

| version | `err.get()` |
|---------|-------------|
| base `8ad206d026` | `nan generated by primitive: log.` ✓ |
| PR `a4b54f8964` | `OUTER check ('check' failed)` — **a check that passed** |

This is supported, tested territory: `test_enabled_errors` parametrizes
div/nan/oob-only error sets over a function containing `checkify.check`, and
`check_error` re-injection is documented as the inverse of checkify — the PR's own
`test_nested_checkify_namespace_collision` exercises exactly this nesting (it
passes only because it has no hole). The failure is silent because `NaNError` and
a no-args `FailedCheckError` both carry zero payload leaves, so unflattening one
with the other's treedef "succeeds". Verification found two more shapes of the
same bug: a vmapped inner checkify (batched error through `_reduce_any_error`)
corrupts the same way, and when the outer check *also* fails, the code tie
misattributes which check fired.

Note on why the repro passes the error as an *argument*: if the inner computation
is inlined under the outer checkify, the outer transformation re-derives its own
NaN check on the same `log` eqn with an earlier code, which happens to shadow the
corrupted entry. That masking is an accident of duplicated checking, not a
defense — the argument-passing form is the documented "stage out, re-inject
elsewhere" pattern.

## F2 — While-loop cond checks burn a code with dropped outputs (bug)

`while_loop_error_check` checkifies the cond jaxpr three times. Instrumenting
every allocation (for a loop whose cond has one check, followed by one more check
after the loop):

| allocation | site | fate |
|-----------|------|------|
| code 0 | pre-loop first-cond application (`checkify_jaxpr(ctx, cond_jaxpr, ...)`, line ~933) | live |
| code 1 | cond re-check inside the checked body (`checkify_while_body_jaxpr(ctx, ...)`, line ~941) | live, carried by the loop |
| code 2 | `checked_cond_jaxpr = jaxpr_to_checkify_jaxpr(ctx, cond_jaxpr, ...)` (line ~950), then `ignore_error_output_jaxpr` drops its error outputs | **burned — hole** |
| code 3 | post-while `checkify.check` | live, fires |

Emitted metadata keys: `[0, 1, 3]`. Re-injection advances the outer context by
`len == 3`, the next outer check gets code 3, and the firing post-while check's
metadata is overwritten. No `errors=` configuration needed — default
`user_checks`:

```python
def inner(x):
  def cond(c):
    checkify.check(c < 100.0, "cond check")   # passes
    return c < 3.0
  out = jax.lax.while_loop(cond, lambda c: c + 1.0, x)
  checkify.check(x < 10.0, "post-while check")  # fires
  return out

err_inner, _ = checkify.checkify(inner)(jnp.array(20.0))

def outer(err, x):
  checkify.check_error(err)
  checkify.check(x < 1000.0, "outer check")     # passes
  return x

err, _ = checkify.checkify(outer)(err_inner, jnp.array(1.0))
```

| version | `err.get()` |
|---------|-------------|
| base | `post-while check ('check' failed)` ✓ |
| PR | `outer check ('check' failed)` — again, a check that passed |

The analogous rules are clean: `cond_error_check` and `scan_error_check` keep
every real-context pass's metadata (verified empirically — contiguous keys,
correct re-injection). The while cond drop and F1's disabled-check path are the
only two burn sources in the file.

## The fixes (validated; commit 1 on this branch)

- **Robust accounting:** `num_codes = max(new_error._metadata, default=-1) + 1`.
  Sound because any code value whose pred can be True has a metadata entry in the
  emitted error — holes are keys that were skipped, never keys missing for live
  values. Verified by induction over every `Error` construction path
  (`assert_func`, the remap, `update_error`'s select merges, placeholder effects,
  `_reduce_any_error`, cond's metadata union, scan/while carries). One caveat for
  the future: a *recharged* error (pred possibly True, `_INACTIVE_CODE`, no
  metadata) violates the invariant, but recharging is currently a no-op; if the
  recharge TODO is ever implemented, that path needs its own design.
- **Don't burn the while-cond codes:** build `checked_cond_jaxpr` with a throwaway
  `CheckifyContext()`. Escape analysis: after `ignore_error_output_jaxpr` only the
  boolean predicate survives, and no checkify rule modifies primal outputs, so the
  codes baked into that jaxpr are dead. Side benefit: the cond pass then always
  starts at code 0, so it shares the `_jaxpr_to_checkify_jaxpr_cached` entry with
  the effects-gathering pass.

## F3 — `_PLACEHOLDER_CODE` deletes cleanly (simplification)

How the sentinel is used today: (1) `_check` bakes `-1` as the code leaf and the
metadata key of the `Error` bound by `check_p` — a trace-time constant, which is
what makes stage 1 deterministic; (2) at discharge, metadata key `-1`
discriminates "fresh check" (allocate one code) from "re-injected inner error"
(offset-remap). Notably the `-1` code *value* is never read — the fresh branch
discards and rebuilds the code dict; only the metadata key matters, and only as a
boolean flag.

The simplification: have `_check` emit code `0` with metadata `{0: meta}`. A
fresh check then *is* a unit-sized inner namespace, and the remap branch handles
it with no special-casing. This deletes the sentinel, the entire fresh-check
branch, and its `assert len(new_error._metadata) == 1` (which a hand-built error
could trip). There is no jaxpr cost: the fresh check's code reaches the discharge
rule as a concrete jaxpr literal, so the remap constant-folds —
`jax.make_jaxpr` output is byte-identical to the PR's. Two independent
implementations converged on the same ~8-line unified body: executable logic
shrinks from two branches / 23 lines to one branch / 8 lines, all tests pass, and
the F1/F2 repros report the right message again (the `max+1` accounting subsumes
both holes; the while fix removes one at the source).

Core of the change (see commit 1 for the full diff):

```python
# _check now builds a unit namespace:
error = Error({effect_type: jnp.logical_not(pred)},
              {effect_type: 0},
              {0: new_metadata},
              {effect_type: new_payload})

# check_discharge_rule: one uniform path replaces both branches:
num_codes = max(new_error._metadata, default=-1) + 1
offset = ctx.current_code
ctx.advance(num_codes)
if offset:
  new_codes = {eff: lax.add(c, np.asarray(offset, dtype=c.dtype))
               for eff, c in new_error._code.items()}
  new_metadata = {k + offset: v for k, v in new_error._metadata.items()}
  new_error = new_error._replace(_code=new_codes, _metadata=new_metadata)
```

## F4 — "First error" ranking changes: one minor, one an improvement

When several checks fire in one run, `Error.get_exception` reports the minimum
code across effect types — so assignment order is user-visible tie-breaking.
Within a single effect type nothing changes (first-in-discharge-order wins on
both versions; verified).

1. **Re-injected errors rank at the `check_error` site** (minor). If a
   re-injected inner error and a later-discharged outer check of a *different*
   effect type both fire, base reports the inner error (its codes were allocated
   when the inner checkify ran), the PR reports the outer check. The common
   idiom — `check_error` immediately after the inner call — is unaffected.
   Inherent to local code assignment; a semantics choice to document, not fix.
2. **User checks no longer outrank all automatic checks** (improvement, and the
   more common configuration). On base, `_check` allocated its code at *trace*
   time while NaN/div/OOB checks allocated at *discharge* time from the same
   global counter — so every user check systematically outranked every automatic
   check regardless of program order. Under `float_checks | user_checks`, a NaN
   upstream of a failing check was reported as the check's message on base; the
   PR reports the NaN — the actual first error, per the docstring. Tests
   asserting base's message could break; worth a line in the change description.

## F5 — Cache-reuse cost of `start_code` in the key (perf note)

Keying `_jaxpr_to_checkify_jaxpr_cached` on `start_code` makes k identical
inner-jit call sites cost k checkify traces (measured: 3 traces vs base's
steady-state 2 for three identical jitted calls). The cond/scan/while
effects-gathering pass runs at start 0, so the real pass misses the cache
whenever the call site sits at a nonzero code. These are traces, not
compilations — probably fine. If it ever matters, the structural fix is to
checkify sub-jaxprs in a local namespace always starting at 0 and remap at the
boundary (for cond branches, pass the offset as an operand so branch bodies stay
cache-identical); that removes `start_code` from every cache key and deletes the
`_record_num_codes` plumbing. Bigger refactor — the current approach is
defensible, and the boundary-remap machinery F3 unifies is exactly the mechanism
such a refactor would generalize.

## F6 — Cross-process nondeterminism survives via placeholder effects (gap)

Not a regression — base has it too — but it is exactly the class of
nondeterminism this PR sets out to kill, and the PR's new tests (flat user
checks, no control flow) cannot see it. `Error._add_placeholder_effects`
iterates `for effect in effects:` over a `set[ErrorEffect]`, staging `jnp.ones`
payload constants in set-iteration order. `ErrorEffect.__hash__` hashes a class
object (id/ASLR-dependent) and `ShapeDtypeStruct`s (`PYTHONHASHSEED`-dependent),
so any checkified program whose cond/scan/while merges two or more error
effects — routine with `errors=all_checks` — lowers to different bytes across
processes. That defeats the persistent compilation cache, the headline benefit
of making codes deterministic.

Verified: a cond merging five effects produces two distinct lowering hashes
across `PYTHONHASHSEED` values on the PR branch. The fix is one line —
`for effect in sorted(effects):` (`ErrorEffect.__lt__` exists for exactly
this) — after which all eight seeds produce one identical hash and the full
suite passes. Commit 2 on this branch.

## F7 — Smaller notes

- `default_checkify_rule`'s `subfuns` branch appears unreachable today — every
  `call_jaxpr`-carrying primitive has an explicit rule (`eval_jaxpr`, pjit,
  remat, cond/scan/while, shard_map, custom_jvp/vjp, hi-call), and even
  `checkify(pmap(f))` routes through the jit rule (instrumented; the branch never
  fires). If it becomes reachable, `num_codes_thunk` depends on the underlying
  tracing cache repopulating aux stores (`lu.cache` does).
- `Error._update`'s metadata merge is silent on key collision (new-wins); that's
  what made F1/F2 silent. After the fix collisions can't happen — a debug assert
  would keep it that way.
- Splitting `_INACTIVE_CODE` (−2) from the placeholder is a good change.
  Inactive codes do get shifted by the remap (to `offset−2`) but only ever pair
  with a False pred, so they are never looked up.
- `next_code` is gone as a module attribute; nothing in-repo references it (nor
  `assert_func`, `ErrorCheckRule`, or the re-signatured `checkify_jaxpr*`
  functions), but they were importable from `jax._src.checkify` — out-of-tree
  registrants of custom `error_checks` rules would break with arity errors;
  worth a mention in the change description.
- The change alters user-observable `Error` internals (code values go from
  1-based process-global to 0-based transform-local) plus the F4 ordering
  semantics, with no CHANGELOG entry — `CHANGELOG.md` has an active Unreleased
  section; worth adding one.
- **Global uniqueness across independent `Error` values is gone by design**: on
  base any two errors ever created had disjoint codes, so interpreting an error
  against the wrong function's metadata failed loudly; now every checkify starts
  at 0, so user code that merges or cross-interprets errors from different
  checkify calls *outside* any checkify scope would silently mis-attribute.
  Inherent to local codes — a contract change to state, not fix.
- Test craft: the multithreaded test would catch the base bug with zero thread
  contention (base fails even two sequential fresh traces); under the PR it
  doesn't stress the one shared state left, the `weakref_lru_cache`. The
  inner-jit and nested tests pass on base too — guard-rails, not bug
  demonstrations. Fine, just worth knowing what pins what.
- Checked clean: vmap/batched re-injection, double-wrap checkify,
  checkify-of-vmap, cond with checks in both branches, scan carries,
  grad-of-custom_vjp, eager checks, x64 mode (one `i64` add per re-injection,
  correct end-to-end), thread-safety of `_jaxpr_to_checkify_jaxpr_cached` (fresh
  `sub_ctx` per computation, no mutation-under-cache; 16 threads × 3 runs, one
  unique lowering), traceback-keyed cache hits (value-based
  `Traceback.__eq__`), and pallas `check_p` lowering (reads
  `metadata.values()`, key-agnostic). Unverifiable here: TPU/GPU pallas paths,
  out-of-tree users of private symbols.
